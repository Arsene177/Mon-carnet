# Mon carnet

Mon carnet lets patients manage emergency information and control which approved doctors can view their medical records.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 5000)
- `pnpm --filter @workspace/medichain run dev` — run the Medichain web app
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — apply DB schema changes to the database selected by `DATABASE_URL` (the Supabase project); verify the target first. It ends by closing every `medichain_*` table to Supabase's public API (row-level security on, no rights or policies for `anon`/`authenticated`; `lib/db/scripts/lockdown.mjs`). New tables must use `.enableRLS()` in the Drizzle schema.
- Run the database schema push after updating an existing environment; patient CM IDs, Supabase sign-in links, two-step sign-in, doctor credential verification, account suspension, epidemic thresholds, booklet verification references, revocable grants, profile locations, in-app notifications, and password recovery requests require the latest schema. Confirm `DATABASE_URL` points to the intended workspace or published production database before pushing.
- `pnpm --filter @workspace/api-server run seed` — seed development demo accounts and sample records
- `pnpm --filter @workspace/api-server run reset-users` — destructive one-time account reset; requires `RESET_ALL_USERS=DELETE_ALL_USERS` and `ADMIN_PASSWORD`, removes all users and linked patient data/attachments, then creates only `arsenedjonkoun5@gmail.com` as admin. Do not run the demo `seed` command afterward.
- `pnpm --filter @workspace/api-server run test:accessibility` — axe-core WCAG 2.2 A/AA rules and 320 px reflow on every screen of every role and the two-step sign-in setup, in French and English (needs the web app built with `pnpm --filter @workspace/medichain run build`, the local Supabase stack like the other tests, and a Playwright Chromium; it also checks that the web app renews its token and that signing out ends the session on the server). Runs in GitHub Actions. What is and is not yet covered, and the rules for new screens and colours: `docs/accessibility.md`.
- `pnpm --filter @workspace/api-server run backup -- --upload` — encrypted backup of the app's tables, the Supabase Auth sign-ins and the attached files (needs `BACKUP_ENCRYPTION_KEY`, at least 32 characters, plus `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, and `pg_dump`/`pg_restore` of the database's major version); `backup:verify`, `backup:restore` and `backup:download` check, restore and fetch backups. Schedule it daily and follow `docs/backup-and-restore.md` (setup, off-site copy, restore procedure, quarterly restore drill). Losing `BACKUP_ENCRYPTION_KEY` makes every backup unreadable.
- `pnpm --filter @workspace/api-server run test` — access-rule, session, two-step sign-in, Supabase, backup and monitoring tests (53) against the built server and a local Supabase stack (`supabase start`, then `eval "$(scripts/supabase-test-env.sh)"` and the schema push with `DATABASE_URL=$TEST_DATABASE_URL`; steps in `docs/supabase.md`). The tests empty the local database and delete every local sign-in, and refuse non-local URLs. The same checks, plus type checking and the French translation check, run in GitHub Actions (`.github/workflows/checks.yml`).
- `pnpm --filter @workspace/api-server run migrate-to-supabase` — one-time, resumable copy of the Replit database and lab files to Supabase (`--dry-run` first). Steps and dashboard settings: `docs/supabase.md`.
- Required env: `DATABASE_URL` — the Supabase session pooler connection string; `SUPABASE_URL` and `SUPABASE_SECRET_KEY` — the project URL and a secret key (server only; the web app holds no Supabase key); `SUPABASE_JWT_SECRET` only for projects still on the legacy JWT secret. Optional: `SUPABASE_STORAGE_BUCKET` (default `medical-attachments`), `SUPABASE_BACKUP_BUCKET` (default `backups`). Required dashboard settings (sign-ups off, higher Auth rate limits, secure password change off): `docs/supabase.md`.
- Optional env: `ALERT_WEBHOOK_URL` — Slack, Discord, Teams or webhook-to-email URL that receives security alerts (no personal data in them); `UNUSUAL_ACCESS_PATIENTS_PER_HOUR` (default 20) — doctors opening this many different patients' records in an hour are reported. Uptime monitors should poll `GET /api/readyz` (checks the database; 503 when it does not answer). Set-up and the weekly check: `docs/monitoring.md`. What to do in a breach or outage: `docs/incident-response.md`.
- Optional env: `CORS_ALLOWED_ORIGINS` — comma-separated origins allowed to call the API from another origin (for example a future mobile app shell). Unset means same-origin only.
- Optional env: `TRUST_PROXY` — number of reverse proxies in front of the API (default `1`), so rate limits see the real client address.
- Rate limits (in memory, per server instance): 5 failed sign-ins per account per 15 minutes, 5 wrong passwords or codes per signed-in account per 15 minutes across two-step sign-in setup and turning it off, new recovery codes, password change and deletion requests, 30 sign-in attempts per address per 15 minutes, 10 registrations and 5 password recovery requests per address per hour, 300 API requests per address per minute. Never commit database dumps; `*.dump` is ignored.

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: Supabase (Postgres) + Drizzle ORM (the shared database layer provided by this workspace)
- Sign-in: Supabase Auth (passwords, sessions, authenticator factors), reached only by the API server
- Files: Supabase Storage (private buckets, signed links)
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

## Architecture decisions

- French and English: user-facing text is written in English inside `t("...")` (`artifacts/medichain/src/lib/i18n.ts`); French lives in `src/lib/i18n-fr.ts`, keyed by the English text, with `{0}`/`{name}` placeholders. Missing French falls back to English. French is the default unless the device prefers English; the FR/EN switch is on the sign-in page and in the header. The choice is stored in the browser and on the account (`preferredLanguage`, `PUT /api/auth/language`), and server-generated notifications use the recipient's language (`artifacts/api-server/src/lib/notification-messages.ts`). Server error messages stay in English and are translated by the web app through the same dictionary. Values stored in the database (record types, regions, statuses) stay in English and are translated only when displayed. After adding or changing UI text, run `pnpm --filter @workspace/medichain run i18n:check`.

- The shared Drizzle layer is used rather than adding a separate Prisma client, to keep one database access stack in this workspace.
- Saved medical records are immutable; a Follow-up must reference an existing record for the same patient.

## Product

Patients have a short `CM`-prefixed ID that is also the booklet access code. Each patient chooses in Access control what happens when a doctor enters it: "Give access automatically" (the default; access lasts until revoked) or "Ask me first" (the doctor's request waits for the patient to approve, with a chosen duration or until revoked, or reject it). Patients and doctors are notified in the in-app inbox; pending requests expire after 7 days, and a doctor whose request was rejected cannot ask again for 24 hours. Requests, decisions, and setting changes are written to the audit log. In automatic mode, entering the CM ID grants an approved doctor immediate access; patients can revoke a doctor's access, which rotates the CM ID to prevent the revoked doctor reconnecting with the old code. Failed code attempts are rate-limited.
Doctors without a CM ID use Emergency lookup: the patient's full name must match exactly (word order, case and accents ignored, and Ŋ, Œ, Æ, Ø, ß, Đ and Ł read as N, OE, AE, O, SS, D and L; partial names and email are not searched), a reason is required, and the date of birth is required when more than 3 active patients share the name. Only emergency details are returned. Each lookup is stored with its reason and hospital, audited, shown to the patient under Emergency lookups, and sent to the patient's inbox when emergency details were shown. Doctors are limited to 10 lookups per hour.
Patient identity: registration requires sex and a date of birth; a patient who does not know the exact date gives an age instead, stored as 1 January of the birth year with `dateOfBirthEstimated` and shown as "born around". The optional national ID card (CNI) number is normalized (upper-case, no spaces or punctuation), unique across accounts, and visible only to the patient and to doctors with granted access; it is never returned to admins, emergency lookups, or pending access requests. Doctors see sex and age next to the patient's name when opening a booklet and in emergency lookups. Admins see possible duplicate patients (same name in any word order and same birth year, unless sexes differ) in User search; accounts are never merged automatically.
Data rights (Law 2024/017 and app-store rules): every account can download its data as JSON from Profile (`GET /api/account/data-export`, audited). Patients and doctors can request account deletion after confirming their password, and cancel while it is pending; administrators cannot (another administrator closes their account). Requests appear under Account requests (the former Password recovery screen) with a 30-day answer target. For a patient the administrator chooses ERASE (account, emergency information, records, coded diagnoses and attached files are deleted; files are removed from storage first, and the patient's own audit events are deleted while doctors' access events stay with the patient reference removed) or CLOSE (sign-in, email, phone, CNI and location removed, all access revoked, inbox cleared, medical records kept). Doctor accounts can only be closed, because their records belong to patients' files. REJECT needs a note, sent to the account holder's inbox. Closed accounts (`closedAt`) cannot sign in or be restored. Deletion requests are kept as evidence after erasure (no foreign key). Records kept after CLOSE are not yet purged automatically: the legal retention period for medical records still has to be confirmed and implemented.
Legal documents: the privacy policy (`/privacy`) and terms of use (`/terms`) are public, bilingual pages in `artifacts/medichain/src/pages/legal.tsx`. They are drafts for legal review; text in [square brackets] (operator name, data protection contact, hosting provider and country, medical-record retention period, liability and jurisdiction clauses) must be completed before launch. Sign-up requires accepting the current version (`LEGAL_DOCUMENTS_VERSION` in `lib/api-zod/src/legal.ts`), and patients must also give explicit consent to the processing of their health data; both are stored with timestamps. Accounts that have not accepted the current version see a consent screen after sign-in (`POST /api/account/consent`, audited). Changing `LEGAL_DOCUMENTS_VERSION` asks every account to accept again.
Doctor account approval enables clinical access. Doctors must submit a professional medical number; an administrator manually verifies it before awarding the certified badge. Verification status is distinct from account approval.
Administrators can suspend or restore accounts without permanently deleting accounts or their medical data.
Patients and doctors can optionally maintain a Cameroon region and arrondissement in Profile. Selectors use the 360 level-3 administrative entries published by OCHA Cameroon through HDX. These are arrondissements, not a verified complete commune/council list. Source: [HDX Cameroon subnational administrative boundaries](https://data.humdata.org/dataset/cod-ab-cmr), Excel resource `cmr_admin_boundaries.xlsx`, [CC BY-IGO](https://creativecommons.org/licenses/by/3.0/igo/legalcode); the source metadata reports boundaries originally created/edited in 1987 and validity from 2019. The bundled names and codes are in `lib/api-zod/src/cameroon-arrondissements.json`.
Admins can filter patient, doctor, and hospital/clinic directories by region and arrondissement; doctor lists can be limited to uncertified accounts. Directory exports are CSV, omit patient contact details and medical records, and are capped at 5,000 entries. Hospitals are grouped by name and location from doctor profiles. Admin notices support all active non-admin users, a region, an arrondissement, or selected users. Recipient IDs are snapshotted at send time, and each account has an in-app inbox.
Admin analytics count distinct patients with suspected, probable, or confirmed structured diagnoses for epidemic-relevant diseases, using onset date (or diagnosis date when onset is missing). It compares the rolling seven-day count with the previous seven days, shows a watch signal from 80% of a per-disease threshold, and raises an in-app alert at the threshold (default: 5). Counts are network-wide because location fields are optional and may be missing; these are review signals, not confirmed outbreaks or public-health diagnoses. Analytics refresh every minute while the admin workspace is open.
Patients can print or save a complete booklet PDF from the Records page. It includes profile and emergency details plus all clinical records, and lists attached files for separate download. Each page repeats the Mon carnet watermark and a server-issued verification reference; the reference confirms issuance and the record count, not that a PDF is unaltered. The browser print dialog must be used to save the PDF.
Every signed-in account can change its password from the dashboard Profile page using the current password.
Users can request password recovery from the sign-in page. Administrators review pending requests, verify the requester through a trusted channel, and generate a random temporary password; requests do not reveal whether an email belongs to an account, and the system never uses a shared default password.
The signed-in web workspace signs out after 30 minutes without pointer, keyboard, touch, or scroll activity and synchronizes explicit sign-out across browser tabs. Idle sign-out also ends the session on the server. Access tokens (Supabase Auth) last about an hour; the web app renews them through `POST /api/auth/refresh` shortly before they expire (`artifacts/medichain/src/lib/session.ts`).
Accounts and sessions are Supabase Auth users and sessions (`docs/supabase.md`); each `medichain_users` row links to one with `auth_user_id`, and the web app reaches Supabase only through `/api/auth/*`. Server-side sign-out: the API refuses a token whose Supabase session no longer exists (`auth.sessions`), so ending a session works at once. Signing out (`POST /api/auth/sign-out`) ends this session. Changing the password and "Sign out of all other devices" (`POST /api/auth/sign-out-other-devices`) end every other session and keep this one. A temporary password from an administrator, a suspension, revoking a doctor and an administrator's two-step reset end every session; restoring a suspended account does not bring its sessions back. Closing or erasing an account deletes its Supabase sign-in. Each is audited (`PASSWORD_CHANGED`, `OTHER_SESSIONS_SIGNED_OUT`, `TEMPORARY_PASSWORD_ISSUED`). When the web app gets a 401 on a signed-in request it forgets the tokens and shows the sign-in page with an explanation. There is no list of individual devices; ending one specific other session is not possible. Accounts copied from the Replit database keep their old scrypt hash in `password_hash` until their first successful sign-in moves the password to Supabase Auth.
Security monitoring (`artifacts/api-server/src/lib/security-events.ts`): locked accounts, sign-in floods, the emergency lookup limit, unusual record access by a doctor, server errors and sensitive administrator actions (two-step sign-in reset, temporary password, suspension, erasure, closure) are stored in `medichain_security_events` (12 months) and listed under System overview › Security events. Warnings go to every other active administrator's inbox and to `ALERT_WEBHOOK_URL`, at most once per 15 minutes per subject; alerts carry no names, emails or health data. Erasure events keep no name of the erased person.
Two-step sign-in (TOTP authenticator app, RFC 6238): required for doctors and administrators, optional for patients. Until it is on, a doctor or administrator account can only use `/api/auth/*` and the consent endpoint (other requests get 403 `MFA_SETUP_REQUIRED`), and the web app shows a setup screen: password, scan the QR code, enter the first code, save 10 single-use recovery codes. Turning it on signs out the other sessions. Sign-in then takes the password and, on a second screen, a 6-digit code or a recovery code (`POST /api/auth/login` returns `mfaRequired: true` without a token until the code is given; wrong codes count toward the account lock). Supabase Auth holds the authenticator factor and its secret and checks codes; the app also refuses a code it already accepted in the last 3 minutes, so each code works once. Recovery codes are the app's own and stored hashed. A recovery code signs in once and removes the lost authenticator: the account then sets up two-step sign-in again (straight away for doctors and administrators), with new recovery codes. New recovery codes need a code from the app. A session that has not passed the second step is refused for any account with two-step sign-in on, so a sign-in made directly at Supabase Auth with only the password cannot be used. Patients can turn it off with their password and a code; doctors and administrators cannot. Anyone can get new recovery codes in Profile. An administrator who has verified the account holder through a trusted channel can reset another account's two-step sign-in from User search; this signs the account out everywhere, notifies its inbox, and is audited (`MFA_RESET_BY_ADMIN`). An administrator cannot reset their own; if the only administrator loses both phone and recovery codes, the reset has to be done in Supabase (Authentication > Users > the account > remove its MFA factor, then set `mfa_enabled_at` to null on its `medichain_users` row). Other audit events: `MFA_ENABLED`, `MFA_DISABLED`, `MFA_RECOVERY_CODE_USED`, `MFA_RECOVERY_CODES_REGENERATED`. A temporary password from password recovery does not remove two-step sign-in.
The patient overview includes an optional profile setup checklist for emergency information, date of birth, contact information, and region. Its progress is not a clinical completeness score.

## Product improvement backlog

The following proposals were reviewed for implementation. Existing foundations (expiring patient grants, access history, linked immutable follow-up records, admin inbox notices and aggregate epidemic signals, and the complete booklet PDF) should be extended rather than duplicated.

### Deferred by request

- AI-assisted clinical summaries or recommendations: not implemented; defer until privacy, clinical validation, consent, and provider choices are designed.
- Cryptographically signed PDFs: not implemented. Patient-friendly summaries and the full booklet use server-issued verification references, but the browser print-to-PDF file itself is not digitally signed and its contents are not cryptographically bound to that reference. A true signed PDF needs a server-side PDF pipeline, protected signing-key lifecycle, signature validation UX, and review of legal acceptance.

### Not implemented in this pass

- Granular consent by record type, declared purpose, and per-record access audit. Current patient grants still cover the existing clinical record scope; add this only with a reviewed database/API migration, clear consent UX, and access-control tests.
- Appointments, medication adherence, patient/doctor follow-up tasks, and scheduled reminders. Linked follow-up records are clinical records, not task or appointment reminders. These features need a persistent workflow model, notification delivery/retry rules, and role-specific controls.
- Patient-doctor secure messaging. The inbox currently contains administrator notices only; do not treat it as a private conversation channel.
- Re-authentication prompts, a list of signed-in devices, and login alerts. Server-side sign-out of all sessions is implemented (see Product); ending one specific device is not.
- Offline/PWA support, clinic/hospital integrations, white-label deployments, richer longitudinal doctor-facing patient summaries, and further operational analytics. Offline health-data storage needs an explicit encrypted storage and conflict-resolution design before implementation.
- Privacy, retention, access/deletion request procedures, legal terms, and regulatory compliance. These require an identified operating jurisdiction, retention and incident policies, and qualified legal/compliance review; do not present the app as certified or compliant until that work is complete.

Patient care summary export, structured doctor note templates, a factual summary of records visible to an authorized clinician, and aggregate network analytics by record type, region, and clinic are now implemented. Regional and clinic activity is suppressed below five distinct patients. Analytics are operational counts, not measures of care quality, and clinic names/locations depend on current clinician profile information.

The delivered improvements across the previous and current implementation passes are the optional patient setup checklist, keyboard skip navigation and focus visibility, reduced-motion support, 30-minute browser idle sign-out with cross-tab sign-out synchronization, patient-friendly care summary printing, structured clinician note templates, a factual doctor-facing patient record summary, and expanded privacy-thresholded aggregate analytics. The 2FA and AI items above are intentionally preserved as future work.
